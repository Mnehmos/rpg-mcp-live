# ADR-H25: Magic effects kernel — generic effect operations, canonical healing, and the first pending-reaction trigger

Status: Accepted; issue #4 implementation slice
Date: 2026-08-07
See also: `docs/hosted-handoff/magic-and-caster-classes-audit.md` (the audit this ADR responds to) and `docs/hosted-handoff/magic-effects-kernel-design-intent.md` (the fuller research/checklist this ADR distills).

## Context

`docs/hosted-handoff/magic-and-caster-classes-audit.md` found that Lantern's magic *architecture* is sound — one class-generic `buildSpellcastingState()` (`src/engine-domain.ts:3819-3849`) correctly derives DC/attack bonus/slots for all 8 caster classes, `learn_spell`/`prepare_spell` correctly branch on known/prepared/spellbook selection mode, and Pact Magic recovery timing is genuinely distinct — but the *executable content surface* is not: `compileSpellEffects()` (`src/content/open5e-import.ts:3525-3573`) only produces a compiled `spell.effect` for spells on a hardcoded 30-entry damage allow-list (`REVIEWED_IMMEDIATE_PRIMARY_DAMAGE_SPELLS`, `:110-140`), because it requires `spell.damageRoll` to exist. Every healing, buff, condition, and summon spell — including Cleric's entire healing identity — is `CONTENT_ONLY`: `resolveCastSpell` correctly and safely rejects them with `content_tier_insufficient` (`src/engine-domain.ts:1370-1377`), but nothing compiles them. Separately, reaction-timed spells (`castingTime === "reaction"`, `:1389-1400`) are gated only by a spent/unspent flag — there is no linkage to an actual triggering event, so Shield (which needs "reaction to being hit" semantics to mean anything) cannot execute at all, since it also has no damage roll and so never compiles in the first place.

ADR-H23 already named the shape of a general reaction record (`PendingReaction`, in that ADR's decision list) as future work once a real Reaction existed to attach it to. This ADR is the first concrete use of that shape.

## Decision

Ship a narrow, horizontal "magic effects kernel" milestone rather than adding more spells to the damage allow-list or attempting per-class fixes:

1. **Generalize the compiled spell effect into a typed effect-operation union**, but implement only two new operation kinds this milestone: `HealingEffect` (dice + ability modifier + upcast scaling + target policy) and `StatModifierEffect` (a timed, duration-bound stat add — Armor Class only, for now). Every other conceivable kind (temporary HP, apply/remove condition, advantage, forced movement, summon) stays out of the executable schema entirely until it has its own milestone — no schema branch may exist without a resolver behind it that can actually apply it.
2. **Cure Wounds compiles as the first healing spell**, resolved by one canonical `applyHealing()` function. Every existing healing source (spell healing, potions/`use_item`, rest) is migrated to call this one function, which owns the max-HP cap and the clear-`unconscious`/reset-death-save-counters semantics in one place — not duplicated per call site.
3. **Shield compiles as the first stat-modifier spell**, but only ever executes through a new persisted `PendingReaction` record (`trigger: "incoming-attack-would-hit"`, storing the originating command, the stored attack roll/total, and the original AC). An enemy attack that would hit pauses before damage is applied, offers eligible reactions, and resumes exactly once regardless of whether the reaction is accepted, declined, or the command is retried with the same `clientCommandId`.
4. **`deriveArmorClass()` is extended, not duplicated**, to fold active timed effects in alongside equipment, with a structured before/after component breakdown (mirroring the explanation-component pattern already used elsewhere for derived values) — there is exactly one AC-deriving function, the same invariant already proven for the equipment-only case.
5. **Magic Missile's executability is downgraded to `UNKNOWN`** pending one direct compiler-and-cast test. The audit's own status matrix and this response's supplemental research disagree about whether Magic Missile's content record actually satisfies the compilation gate — that disagreement gets resolved by a test, not by re-reading comments, before either claim is trusted again in future audits.
6. **Any effect path (e.g. an `improvise`-style fallback) that can return a committed success without a corresponding state mutation is treated as a defect to fix or reject in this same milestone** — narrative-only success is exactly the failure mode the rest of the engine's atomic-commit design exists to prevent, and it must not be allowed to survive under a different code path than `cast_spell`'s own.
7. **Scope fence**: this milestone does not touch the damage-spell allow-list, class progression/leveling (already a separate open product decision per the magic audit), NPC caster architecture, or anything from the reference engine (already fenced by ADR-H13). Each is explicitly out of scope here, not silently deferred.
8. **Operational prerequisite, adopted alongside this ADR but not itself a design decision**: before this milestone's implementation work begins, the previously-uncommitted Lantern working tree (`git status` showed zero commits as of both the action-economy and magic audits) is swept for secrets, `.gitignore` completeness is confirmed, and a baseline commit is created.

## Consequences

- The compiled-spell-effect type becomes a discriminated union instead of a single damage-only shape; the 30 existing allow-listed damage spells must be adapted to the new union with no behavior change (their existing tests must keep passing unmodified in outcome).
- `resolveCastSpell` gains a second effect-kind branch (healing) parallel to its existing damage branch, plus a new pause/resume resolution path for pending reactions — this new "paused" resolution shape must fit inside the existing idempotency/version-conflict transaction contract (ADR-H11, ADR-H15) rather than becoming a second, competing commit mechanism.
- Every existing healing-adjacent code path (rest, `use_item`) needs to be checked against the new canonical `applyHealing()` for the unconscious/death-save-reset gap flagged as `UNKNOWN` in the source research — if real, fixing it only inside Cure Wounds would leave the same defect live in rest and potions.
- Magic Missile moves from "assumed implemented" to "explicitly unverified" in tracking until its dedicated compiler-and-cast test lands; any future audit's spell-family matrix should reflect that, not the magic audit's original (now-superseded) "Yes, but... UNKNOWN" entry.
- Healing, buff, condition, and summon spells beyond Cure Wounds and Shield remain `CONTENT_ONLY` after this milestone — this is one narrow proof slice per family, not a broad content push.

## Rejected alternatives

- **Special-casing Cure Wounds and Shield as bespoke spell-name branches inside `resolveCastSpell`**: rejected — it would reproduce the exact hardcoded-allow-list pattern that produced the damage-only gap in the first place. The generic effect-operation union is what makes the *next* fifty spells cheap to add instead of each needing its own resolver branch.
- **Implementing the full effect-operation union (temp HP, conditions, advantage, forced movement, summon) in this same milestone**: rejected — shipping only two operation kinds keeps each provably correct before the vocabulary grows further; the remaining kinds get their own future ADR (a "Conditions Kernel" milestone, per the sequencing in the design-intent transcript).
- **General pause-and-resume for every trigger, including mandatory/NPC-caused ones**: rejected, consistent with ADR-H23's existing position — `PendingReaction` pauses only for a reaction that requires a genuine player choice; deterministic/mandatory effects continue to resolve inline within one atomic commit.
- **Bundling NPC spellcasting or class-progression fixes into this milestone**: rejected — both are real, larger gaps the audit identified, but neither blocks proving the effect-operation pattern works end-to-end, and bundling them would delay shipping a narrow, independently verifiable slice.
